# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

"Les Secrets de Cassis": a mobile web treasure-hunt game, one phone per team, with a live organiser dashboard. Plain HTML + vanilla JS, **no dependencies, no build step**. Hosted as static files on GitHub Pages. UI text, comments and docs are in French: keep them that way.

## Commands

- Run all tests: `node --test test/engine.test.js test/pages.test.js test/sync.test.js` (Node 22 rejects a bare directory like `test/`). `pages.test.js` checks that every `<script>`/`<link>` in the three HTML pages exists and that every JS file parses; adding a file means adding its tag to the page, and a file not referenced by any page fails the test.
- Run one test: `node --test --test-name-pattern="normalisation" test/engine.test.js`
- Several tests load the real `contenu.js` and check its zone ids (e.g. `zones[2].A[0]` answers "Eglise Saint-Michel", circuit of team E6). Editing the demo content can break them.
- Regenerate the publishable `game.js` from `contenu.js` (validates first, exits 1 on errors): `node outils/publier.js`
- Run locally: open `index.html` directly (`file://`) or serve on localhost. Add `?equipe=E1` to play as a team, `?reset` to wipe local progress.

## Architecture

**Two content files, one secret.**
- `contenu.js` sets `window.GAME_SOURCE`: teams, circuits, puzzles, **answers and codes in plain text**. Git-ignored; must never be published. Its header comment documents the step types and fields.
- `game.js` sets `window.GAME`: generated by `Engine.publishedFile()` (via `outils/publier.js` or the download button in `outils.html`). Answers become `step.h` hashes; `masterCode` becomes `masterHash`; `adminCode` and the team `key`s are dropped (no hash, no ciphertext: nothing in `game.js` lets anyone test the dashboard code offline). `Engine.secretsSql()` (written to the git-ignored `supabase-equipes.sql` by `publier.js`, or via a button in `outils.html`) holds the team keys and the plain answer book (`answerBook`: answers + `masterCode` + team keys), loaded into Supabase tables only the organiser can read. Never edit `game.js` by hand; regenerate after every change to `contenu.js`, and re-run `supabase-equipes.sql` in Supabase.
- `index.html` and `admin.html` load `game.js`, then inject `contenu.js` via `document.write` only on `file:`/localhost. Code reads `window.GAME_SOURCE || window.GAME`, so every check must work with both plain values and hashes (see `checkAnswer`/`answerHashes` and `codeMatches(input, plain, hashed, salt)`).
- Hashing is cyrb53 (sync, works on `file://`). It obfuscates answers and is not real security; puzzle text stays readable in `game.js`.

**`js/core/*`: pure logic, no DOM.** Seven small UMD modules (`text`, `path`, `time`, `geo`, `scoring`, `validate`, `publish`) that each add to `window.Engine` in the browser (loaded in that order by the `<script>` tags, dependencies read from the namespace at call time); in Node, `require('js/core/index.js')` merges them. Shared by the game, the dashboard, the tools page, the tests and `publier.js`. Put any testable logic here: answer normalisation (case/accents/punctuation ignored, `ST`→`SAINT`, `match: 'contains'` tries every contiguous word sequence), `buildPath` (flattens a team's circuit into steps with `key = z{zone}-{variant}-{i}`, then appends `final`), penalties/timing, GPS distance, `tap` hit-testing, badges, ranking, `validate`, `simulate` (zone occupancy per slot), `publish`.

**Game model.** `zones[id]` holds variants `A`/`B`, each a list of steps. A team has a `circuit` (ordered zone ids) and a `variant` (string, or a per-zone object). The first step of each zone is the riddle that leads *to* that zone, so any circuit order works. Tests assume that for the demo content no zone ever has more than 2 teams in a slot, and that teams sharing a slot use different variants.

**Front-ends** (each one is an IIFE that renders HTML strings into a root element):
- `js/player/*` (player, namespace `window.EscapePlayer`; `context.js` first, `main.js` last with the boot code and top-level side effects; shared mutable state such as `state`/`path`/`remote` lives on that namespace): state is kept in `localStorage` under `escape:{GAME.id}` and synced to other tabs through the `storage` event (a scanned checkpoint QR opens a new tab with `?scan=`). Pushes are debounced to Supabase, plus a 30 s heartbeat. Works offline. If a phone dies, another phone can resume the team from its server row.
- `js/admin/*` (dashboard, namespace `window.EscapeAdmin`, same layout: `context.js` first, `main.js` last): code-gated by Supabase Auth only (the `adminCode` is the organiser account password; no local check), reads the answer book from Supabase (`organiser_book`), polls Supabase every 10 s, flags stuck teams, and warns if `contenu.js` is reachable on the deployed site.
- `js/tools/*` (prep tools, namespace `window.EscapeTools`, loads `contenu.js` directly): validation, circuit simulation, `game.js` download, printable QR codes generated locally by `js/shared/qrcode.js` (self-contained encoder, byte mode, EC level M, versions 1-10).
- `js/shared/sync.js` (and `js/shared/util.js` for `Util.esc`): Supabase REST calls through raw `fetch` (no client lib) on `progress` (`team` PK, `data` jsonb) and `messages`. Disabled when `config.js` has empty `supabase.url`/`key`. The schema, RLS policies and `team_*` functions live in `supabase.sql`. Keys starting with `eyJ` (legacy anon JWT) also get sent as `Authorization: Bearer`.

`config.js` contains only public values (`publicUrl` used for QR codes, Supabase URL + publishable key, `adminEmail` of the organiser account).

**Supabase access (auth layer).** The publishable key (role `anon`) has no direct access to the tables (see `supabase.sql`). Phones call `team_*` SQL functions through `rpc`, each checking the team's secret `key` (`teams.E1.key` in `contenu.js`, stored in the closed table `team_secrets` via the generated `supabase-equipes.sql`, git-ignored). The key travels in the team QR code (`?equipe=E1&k=…`), is kept in localStorage apart from the state, and never appears in `game.js` (stripped by `Engine.publish`; the dashboard reads it from the `organiser_book` table to draw the QR codes). The dashboard signs in with Supabase Auth (email from `config.js`, password = normalised `adminCode`), needs `app_metadata.role = 'organisateur'`, and uses the token for `loadAll`/`deleteAll`/chat. In `js/shared/sync.js`, player functions are `team*` and organiser functions are the rest; never mix them.

CSS is split per page in `css/player/`, `css/admin/` and `css/tools/` (one file per component); the link order in the HTML matters, since it reproduces the original cascade. The three HTML pages stay at the repo root (printed QR codes point there).
